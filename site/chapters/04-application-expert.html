CHAPTER 04

从“会聊天”
到 AI 运用层专家

真正的高手不是能写一段神奇 Prompt，而是知道：这个任务该给模型什么上下文、何时检索、何时调用工具、何时使用确定性流程、什么时候才值得上 Agent，以及怎么证明系统真的可靠。

设计能力把真实工作拆成 AI 能处理的任务、数据与动作。
系统能力选择 Context、RAG、Tool、Workflow、Agent 等组件。
工程判断用 Eval、权限、成本和错误代价约束 AI。
运用层专家的核心公式

结果质量 ≈ 模型能力 × 上下文质量 × 工具/数据质量 × 工作流设计 × Eval 与纠错。

如果把所有问题都归结为“模型不够聪明”，你就很难成为真正的 AI 使用专家。很多失败不是模型能力不足，而是上下文缺失、检索错误、工具无权限、任务拆解不清、输出无法验证，或者根本用了错误的系统架构。

4.1 · TASK ANATOMY

第一步永远不是写 Prompt，而是拆任务

面对一个真实工作，先拆成五个问题：

输入用户问题、文件、数据库、网页、图片还是历史对话？
认知任务抽取、分类、总结、生成、推理、规划还是比较？
外部知识模型参数里没有的哪些事实必须实时取得？
行动只需输出文本，还是要搜索、发邮件、改数据库、写代码？
验收标准什么叫正确？谁检查？错误能否自动发现？
错误代价错一次只是重写，还是会造成付款、法律、医疗或生产事故？
为什么这一步比 Prompt 更值钱

企业工作往往不是一道题，而是一串跨系统流程。能把流程拆清楚的人，才有能力判断哪些步骤适合 AI，哪些必须保留确定性代码或人工责任。

4.2 · PROMPT

Prompt 是“当前这次调用的指令”，不是全部上下文

好的 Prompt 主要解决四件事：告诉模型要做什么、依据什么、输出成什么样、什么不能做。

ROLE / GOAL任务目标

你要模型完成什么，而不是堆“你是一位世界级专家”。

INPUT输入事实

把当前任务真正需要的数据、定义和边界给进去。

CONSTRAINT约束

来源、格式、长度、禁止事项、判断标准。

OUTPUT输出契约

人读的文字，还是下游程序要解析的 JSON / 字段？

不要迷信“万能 Prompt 模板”

如果任务需要实时数据、企业文件、数据库或软件操作，再精巧的 Prompt 也不能替代缺失的 Context 和 Tool。

4.3 · CONTEXT ENGINEERING

Context Engineering：决定“模型这次到底看见什么”

上下文不仅是你的最后一句 Prompt。它可以包括系统规则、用户历史、文件片段、搜索结果、数据库记录、工具状态、示例、时间、权限和前面步骤的中间结果。

系统规则角色、权限、边界、安全策略
任务指令当前目标和输出要求
用户 / 业务状态历史、偏好、账户、工作流阶段
外部知识检索、网页、数据库、文件
示例好输出 / 坏输出 / few-shot demonstrations
工具反馈API 返回值、报错、环境状态

“上下文窗口越来越长”也不等于可以把一切资料无脑塞进去。研究显示，模型对长上下文中的信息利用并不总是均匀，关键证据的位置、噪声和上下文结构都会影响表现。

运用原则

不是 Context 越多越好，而是让“此刻决策真正需要的信息”尽可能准确、相关、结构清晰地进入模型。

4.4 · RETRIEVAL-AUGMENTED GENERATION

RAG：先找证据，再让模型回答

用户问题“公司差旅政策是什么？”
→
检索从公司文档找相关片段
→
组装 Context问题 + 证据 + 来源
→
生成基于证据回答

RAG 的根本动机是把“模型参数中的隐性记忆”和“可更新、可引用的外部知识”分开。2020 年提出的 Retrieval-Augmented Generation 就明确把参数化模型和外部非参数化记忆结合起来。

适合 RAG

知识会更新、需要出处

公司政策、产品文档、法规、研究资料、客户知识库。

不一定需要 RAG

只是常识生成或固定格式

改写一段文字、头脑风暴、简单格式转换。

RAG 不是“解决幻觉”的魔法按钮

检索错了、切块错了、排名错了、证据矛盾或 Prompt 没要求引用，最终输出仍然会错。RAG 本身也必须被 Eval。

4.5 · STRUCTURED OUTPUT

当结果要进入程序，别让模型自由发挥格式

人类可以读一段自然语言再理解字段，但软件工作流更需要稳定 Schema。比如抽取发票时，不要只说“整理一下”，而是要求固定字段：

{
  "invoice_no": "INV-2026-0182",
  "supplier": "Example Ltd.",
  "amount": 1250.00,
  "currency": "USD",
  "due_date": "2026-11-01",
  "confidence": 0.94
}

结构化输出让 AI 从“聊天界面”更容易升级成系统组件：它可以被校验、存数据库、触发条件分支、进入下一步工具调用。

4.6 · TOOL USE

模型不擅长的事情，应该交给工具

实时事实搜索 / 数据库 / API

不要让模型凭记忆猜今天的价格、库存、天气、航班。

精确计算计算器 / Python / SQL

语言模型负责决定怎么算，计算工具负责真正算。

外部行动Email / CRM / Calendar / Browser

模型决定是否需要行动，工具承担真实副作用。

专用模型OCR / Vision / Speech

一个系统可以同时编排多种最适合的模型。

Toolformer 等研究说明，语言模型可以学习何时调用外部工具；ReAct 则把推理与行动交错起来，让模型根据外部观察更新计划。这些思想构成今天 Agent 系统的重要基础。

4.7 · WORKFLOW vs AGENT

能用 Workflow 解决，就不要为了“高级”硬上 Agent

WORKFLOW

流程由人预先定义

步骤稳定、路径有限、合规要求高时，用确定性编排更可靠。

  • 提取 → 校验 → 写入数据库
  • 分类 → 路由 → 固定模板回复
  • 定时报告 → 人工确认 → 发送
AGENT

下一步由模型动态决定

任务路径难预先穷举，需要搜索、探索、反复尝试时，Agent 更有价值。

  • 开放式研究
  • 复杂软件操作
  • 多源问题排查
Goal目标
→
Reason判断下一步
→
Act调用工具
→
Observe读取结果
↺
Stop满足完成条件
Agent 的最大问题不是“不会想”，而是错误会累积

一次 95% 正确的步骤，连续执行很多步后总体成功率会显著下降。长任务因此需要检查点、重试、状态管理和停止条件。

4.8 · EVALUATION

没有 Eval，就没有可持续的 AI 系统

“我试了十次感觉不错”不是评测。最基础的 Eval 是建立一组代表真实任务分布的测试案例，并定义明确成功标准。

L1输出格式

JSON 能不能解析？必填字段有没有？

L2事实正确

答案是否被给定证据支持？

L3任务成功

工具是否真的执行了正确动作？

L4业务结果

是否减少工时、提高转化、降低错误或提升客户满意度？

模型升级、Prompt 修改、RAG 检索策略变化之后，都应该重新跑同一套 Eval。否则你无法知道“新版本”到底变好了还是只换了一种风格。

4.9 · PRODUCTION

生产环境真正关心：可靠性、权限、延迟和成本

可靠性

超时、重试、Fallback、结果校验、异常路径。

权限

模型能读什么、能写什么、哪些动作必须人批。

安全

Prompt Injection、恶意文件、数据泄露、越权调用。

延迟

用户能等 300ms、3 秒还是 3 分钟？

成本

Token、检索、工具、重试、长上下文、人工复核。

可观测性

记录输入、模型、工具轨迹、错误和结果，才能调试。

一个关键商业判断

Demo 的成本只看“模型调用多少钱”；真实产品的成本要算模型 + 数据 + 工具 + 重试 + 人审 + 错误损失 + 运维。单位经济性往往在这里才真正显现。

4.12 · SELF CHECK

本章自测

Q1：Prompt Engineering 和 Context Engineering 最大的区别是什么？

Prompt 主要是当前调用的任务指令；Context Engineering 关心模型在这一时刻能看到的全部信息，包括系统规则、历史、文件、检索结果、工具状态和示例。

Q2：什么时候应该用 RAG，而不是直接把所有文档塞进长上下文？

文档很多、会更新、需要按问题选取证据或需要引用来源时，RAG 往往更高效；长上下文本身也可能存在注意力利用不均和成本问题。

Q3：为什么 Workflow 往往比 Agent 更适合企业生产？

如果流程路径稳定，确定性 Workflow 更容易测试、审计、控制权限和保证可靠性。Agent 适用于无法预先穷举路径的开放任务。

Q4：为什么 Eval 是运用层专家的核心能力？

因为没有稳定测试集，就无法判断模型、Prompt、RAG 或工具改动是否真正提升了业务成功率，也无法控制回归。
