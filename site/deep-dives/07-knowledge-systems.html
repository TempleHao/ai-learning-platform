DEEP DIVE 07

RAG、Memory 与 Knowledge Systems

强模型不等于知道你公司的制度、今天的库存、客户刚刚发来的邮件、某份合同第 17 条，或者你上周为什么做了某个决策。真正可用的 AI 系统，需要一层可检索、可更新、可授权、可追溯的知识基础设施。

概念彻底区分 Parametric Knowledge、Context、RAG 与 Memory。
工程理解 Chunking、Embedding、Hybrid Search、Rerank、Metadata 与 Eval。
企业知道知识系统真正难在权限、更新、来源、责任和维护，而不是向量数据库。
一句话框架

模型负责“理解和生成”；知识系统负责“把当前任务真正需要的事实，在正确时间、按正确权限送进模型上下文”。

D7.1 · THREE KNOWLEDGE LAYERS

AI 系统里至少有三种完全不同的“知道”

PARAMETRIC

模型参数里的知识

训练过程中压缩进权重的模式、语言和事实。

优点：快、通用。缺点：难更新、难追溯。
CONTEXT

这一次调用看见的信息

Prompt、文件片段、工具结果、当前对话、系统指令。

优点：即时。缺点：窗口有限、太多会稀释重点。
EXTERNAL STATE

外部知识与记忆

数据库、文档、搜索、CRM、Memory files、事件日志。

优点：可更新、可审计。缺点：必须检索和治理。

很多“模型胡说”的根因并不是模型太笨，而是它根本没有接触到正确的事实源，或者系统取回了错误的片段。

D7.2 · RAG PIPELINE

RAG 不是“向量数据库”，而是一条完整证据流水线

① Ingest解析文档、表格、网页、附件。
→
② Chunk切成可检索单元。
→
③ IndexEmbedding + 关键词 + Metadata。
→
④ Retrieve根据问题取候选证据。
→
⑤ Rerank重新排序最相关片段。
→
⑥ Generate带来源生成回答。

OpenAI 当前的 File Search 也是这个思想：模型在生成前可以对已上传知识库做语义与关键词检索，并可按 Metadata 过滤。真正要优化的，是“取回什么证据”，而不只是最后的 Prompt。

D7.3 · RETRIEVAL IS THE HARD PART

一个很反直觉的事实：RAG 的瓶颈经常不在生成，而在检索

没取到正确答案明明在资料里，但检索没有命中。
取错了关键词相似，却不是当前问题需要的文档。
取旧了同一制度有多个版本，系统拿了过期版。
取太多大量无关片段占满 Context，反而降低回答质量。
权限错了取到了用户本来无权看的知识。
答案超证据模型根据证据又“补了一点”，造成事实漂移。
RAG Debug 原则先问“证据找对了吗？”，再问“模型回答得好吗？”
D7.4 · CHUNKING + HYBRID SEARCH

检索质量来自很多小决策，不是换一个 Embedding 就解决

Chunk Size太小没上下文，太大又混入太多主题。
Chunk Boundary按字符切，还是按标题、段落、表格、章节语义切？
Semantic Search擅长意思相近，即使关键词不同。
Keyword / BM25对产品型号、编号、专有名词、精确短语很重要。
Metadata Filter部门、时间、客户、版本、权限可以先缩小范围。
Reranker对候选结果做第二次更精细排序。

成熟企业系统常常使用 Hybrid Retrieval：语义检索 + 关键词检索 + Metadata + Reranking，而不是“向量相似度一把梭”。

D7.5 · MEMORY ≠ RAG

Memory 解决“跨任务记住什么”，RAG 解决“从知识库找什么”

RAG

知识检索

从已有知识源里找到当前问题的证据。

  • 制度
  • 合同
  • 产品文档
  • 历史邮件
  • 知识库
MEMORY

经验与状态

跨会话保留用户、项目或 Agent 自己学到的信息。

  • 偏好
  • 历史决策
  • 任务进度
  • 失败教训
  • 长期状态

Anthropic 的 Memory Tool 就是一个很清晰的例子：Agent 可以把信息存成持久文件，需要时再读取，而不是永远把全部历史塞在上下文窗口里。

D7.6 · CONTEXT BUDGET

Context Window 不是垃圾桶：越大不代表塞得越多越好

现实工作会不断产生文件、搜索结果、日志、工具输出和历史对话。如果全部保留，系统会变慢、变贵，也会把真正重要的信息淹没。

STABLESystem / Rules

长期稳定的行为约束。

JUST-IN-TIMERetrieved Evidence

当前任务真正需要的外部事实。

WORKINGCurrent State

当前计划、临时结果、未完成步骤。

PERSISTENTMemory

值得跨任务保存，但不必每次加载。

Context Engineering 的新趋势

更强模型并没有让 Context Engineering 消失，反而让重点从“塞更多提示词”转向“按需读取、动态压缩、把长期知识留在外部”。

D7.7 · PERMISSION-AWARE KNOWLEDGE

企业知识库最危险的问题之一：AI 不能因为“能搜到”就“应该看到”

知识系统必须继承原系统的权限边界。否则一个原本只能看自己客户的销售，通过 AI 问一句“总结所有客户合同”，就可能越权获得敏感数据。

ACL / Identity检索前先确认用户是谁。
Source Permission源系统权限要传递到索引和检索层。
Version知道哪份文档当前有效。
Provenance回答必须能追到来源。
Retention知识多久保留、什么时候删除。
Audit谁搜了什么、取回了什么、回答了什么。
D7.8 · RAG EVAL

RAG Eval 必须拆成至少两层

RETRIEVAL

证据有没有找对？

Recall@K、Precision、MRR、NDCG、人工相关性评分。

这是 Search 问题。
ANSWER

回答有没有基于证据？

正确性、完整性、引用覆盖、Faithfulness、拒答能力。

这是 Generation 问题。

如果检索没命中，换 Prompt 没意义；如果检索正确但回答错误，再去优化模型、提示、格式或验证。两层必须分开测。

D7.10 · ENTERPRISE KNOWLEDGE LAYER

真正的企业 Knowledge Layer，不只是一个聊天机器人

SOURCESDocs · Drive · Email · CRM · DB · Tickets · Web
↓
INGESTIONParse · Normalize · Version · Permission · Metadata
↓
RETRIEVALKeyword · Semantic · Filter · Rerank · Graph / SQL
↓
CONTEXTEvidence Selection · Compression · Citation
↓
APPLICATIONSSearch · Copilot · Agent · Analytics · Workflow

一旦这一层做好，它不只服务“问答机器人”。同一套知识基础设施可以给销售 Copilot、客服 Agent、研究系统、代码 Agent、风控流程和管理决策同时提供可信 Context。

D7.11 · ECONOMICS

企业知识系统的价值，通常不是“回答更聪明”，而是降低搜索与协调成本

01

减少找资料时间

知识工作中大量时间消耗在找文件、问人、确认版本。

02

降低新人上手成本

组织隐性知识可以被更快检索和解释。

03

让 Agent 可执行

没有业务 Context 的 Agent 只能做通用动作，接入 Knowledge Layer 才能真正理解组织。

04

形成数据飞轮

查询、点击、引用、纠错和任务结果都可以反过来改进知识质量。

但成本也会从“模型调用”扩展到文档摄取、索引更新、权限同步、检索基础设施、重排、追踪、人工治理和长期维护。

D7.13 · FRONTIER · 2026

知识系统正在从“RAG Chatbot”走向 Agent Context Infrastructure

2026 年更明显的趋势，是检索、Memory 和 Context Management 逐渐合流：Agent 不再把所有历史都塞在窗口里，而是把知识、经验和状态留在外部，需要时 Just-in-Time 读取。Anthropic 甚至把更先进模型上的系统 Prompt 大幅精简，强调动态 Context Engineering。

HybridSemantic + Keyword + Metadata + Rerank企业检索越来越不是单一向量搜索。
JITJust-in-time context retrieval长期 Agent 更依赖按需加载，而不是无限堆 Context。
ACLPermission-aware retrieval权限继承成为企业知识系统能否真正部署的关键。
D7.14 · SELF CHECK

本页自测

为什么 RAG 不能简单等同于向量数据库？

RAG 是从摄取、切块、索引、检索、过滤、重排到生成和引用的完整证据流水线。向量数据库只是其中一个组件。

Memory 与 RAG 的核心区别是什么？

RAG 从已有知识源检索当前问题的证据；Memory 负责跨任务保存用户、项目或 Agent 过去学到的状态与经验。

为什么检索 Eval 和回答 Eval 要分开？

否则你无法判断失败来自“没找到正确证据”，还是“证据找对了但模型没正确使用”。两类问题的修复方法完全不同。

企业 RAG 最容易被低估的工程问题是什么？

权限、版本、新鲜度、来源追踪和维护成本。这些往往比 Embedding 模型本身更决定是否能生产部署。
