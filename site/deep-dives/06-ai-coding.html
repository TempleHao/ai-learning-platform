DEEP DIVE 06

AI Coding、Vibe Coding 与软件工程新范式

AI 编程正在重写软件生产分工。Agent 可以读仓库、改多个文件、运行命令、执行测试、修 Bug、提 PR；人的重心因此转向定义问题、提供上下文、设计验收、控制风险和审查结果。

使用者知道什么时候可以大胆 Vibe，什么时候必须收紧工程约束。
Builder学会把仓库、测试、文档和任务拆解改造成适合 Agent 工作的环境。
商业判断理解为什么软件供给成本下降，会同时创造新产品和摧毁旧壁垒。
核心变化

过去 IDE 的中心是“文件”。Agentic Coding 的中心越来越像“任务”。用户描述目标，Agent 自己读取仓库、选择文件、运行工具并迭代，最终交付一个可审查的结果。

2026 年的主流 coding agent 已经明显超出补全代码的范畴。GitHub 的 Agent Mode 可以自行决定修改哪些文件并运行命令；OpenAI Codex 面向从 issue 到 tested PR 的完整工程任务；Claude Code 也强调 read → plan → act → observe 的 agent loop。软件工程正在从“人驱动每个步骤”转向“人监督任务闭环”。

D6.1 · MATURITY LADDER

从代码补全到 AI-native Software Factory

LEVEL 1

Autocomplete

AI 猜下一行 / 下一段代码。

人负责全部架构与执行。
LEVEL 2

Chat Coding

解释代码、生成函数、帮忙 Debug。

AI 是问答助手。
LEVEL 3

Vibe Coding

人描述想要的结果，AI 快速生成和修改产品。

适合探索与低风险原型。
LEVEL 4

Agentic Coding

Agent 读仓库、改文件、跑测试、执行终端并反复修正。

任务成为基本单位。
LEVEL 5

Parallel Agents

多个 Agent 并行处理 Bug、测试、迁移、功能和 Review。

人负责调度与合并。
LEVEL 6

AI-native Factory

Issue / 需求进入系统后，由 Agent 持续执行、验证、提 PR、监控和维护。

软件生产流程本身被重构。
D6.2 · WHY VIBE CODING WORKS

Vibe Coding 为什么突然变得可行？

传统编程要求人把“想做什么”翻译成精确语法。大模型降低了这层翻译成本：人可以先表达目标、界面、业务逻辑和错误现象，再让模型把意图转成代码。

01

自然语言变成接口

需求不必先被完全翻译成代码语法，人可以直接表达业务意图。

02

代码先验极强

模型训练中见过大量库、框架、模式和常见错误，可以快速组合成熟结构。

03

反馈周期缩短

“改一下 → 跑一下 → 看结果 → 再改”可以在分钟级反复进行。

04

探索成本下降

以前不值得专门排期的小工具、内部应用和一次性自动化，现在可能值得做。

最深的商业变化

软件开发成本下降会直接扩大软件供给：一批过去“不值得开发”的长尾工具和内部系统开始具备经济可行性。

D6.3 · WHY VIBE CODING BREAKS

Vibe Coding 最大的危险：局部看起来都对，整体越来越不可控

Agent 非常擅长在局部上下文里完成一个具体改动，但软件系统会积累状态、依赖、约束和历史决策。如果每次只说“这里再改一下”，模型可能不断叠加补丁，最终形成隐藏耦合和不可预测行为。

需求漂移每轮 Prompt 都改变一点目标，却没有统一 Spec。
上下文丢失Agent 不知道几周前为什么做了某个架构选择。
重复实现没找到已有模块，又写一套类似逻辑。
隐性回归当前功能好了，却悄悄破坏其他路径。
安全债务为了“先跑起来”绕过权限、校验、密钥或输入安全。
不可解释技术债用户不知道代码为何这样写，也不知道哪里不能动。
成熟 Vibe Coding 的分水岭系统必须具备机器可读取的工程约束：规格、测试、边界、权限和验收标准。
D6.4 · AGENT-FRIENDLY REPOSITORY

未来的好仓库，不只要让人看懂，也要让 Agent 看懂

Agent 每次开始工作都需要重新建立世界模型。仓库越清晰，它花在“猜这项目到底怎么回事”上的 Token 和错误就越少。

MISSIONREADME / 产品目标

这个项目解决什么问题，不解决什么问题。

RULESAGENTS.md / CLAUDE.md / Instructions

代码规范、禁止事项、运行方式、架构原则。

MAP架构图 / 目录说明

模块边界、数据流、关键依赖。

VERIFYTests / Lint / Typecheck / Eval

什么叫“改对了”，最好由机器自己验证。

STATEIssues / ADR / Changelog

为什么这样设计、当前欠账、历史决策。

这类文档过去常被视为“工程洁癖”，在 Agent 时代却直接影响产能：它们其实是在给 AI 构建长期 Context。

D6.5 · SPEC-FIRST

复杂任务不要从“开始写代码”开始，要从“验收标准”开始

① Goal用户最终想得到什么？
→
② Constraints不能破坏什么？权限和技术限制是什么？
→
③ Acceptance怎样证明任务完成？
→
④ Plan哪些文件 / 模块需要变化？
→
⑤ ExecuteAgent 修改和验证。

一个成熟任务描述应该尽量包含：现状、目标、非目标、边界条件、示例、验收标准、允许修改范围。信息越完整，Agent 越能把任务当成工程问题来处理。

Prompt 长度从来不是目标

高价值 Context 要放在正确位置：稳定规则进仓库说明，单次任务进 Issue / Spec，动态状态通过工具读取。

D6.6 · TESTS AS MACHINE LANGUAGE

在 Agent 时代，测试同时承担质量控制和机器验收两项职责

人可以看界面说“差不多对了”，Agent 需要更明确的反馈。如果测试、类型检查、Lint、截图比较、性能基准或业务 Eval 可以自动运行，Agent 就能形成闭环：

实现修改代码
→
运行验证Tests / Build / Eval
→
读取失败错误日志
→
修正再次修改
↺

OpenAI 在介绍其 agent orchestration 实践时特别强调了 agent-friendly repository、自动测试和 guardrails。原因很简单：如果系统自己不知道“成功是什么”，Agent 只能不断凭感觉写代码。

D6.7 · HUMAN REVIEW

AI 写更多代码后，人类工程师的价值不会等比例下降

Anthropic 对约 40 万次 Claude Code 会话的研究发现，一个有意思的分工模式是：人类通常做更多“做什么”的规划决策，Agent 做更多“怎么做”的执行决策；而领域经验更高的人，往往能让 Agent 每次指令完成更多工作。

AI 更适合

执行密集工作

  • 搜代码
  • 机械迁移
  • 生成测试
  • 重构
  • 修重复 Bug
  • 文档同步
人更关键

高杠杆判断

  • 需求取舍
  • 架构边界
  • 安全 / 风险
  • 异常判断
  • 产品体验
  • 最终责任
专家的杠杆正在变大

当执行变便宜，能够定义正确问题、识别坏方案和设计验证机制的人，可以控制更多软件产出。

D6.8 · BLAST RADIUS

Agent 越强，权限设计越重要

一个只能给代码建议的 AI，最坏通常只是建议错；一个能运行 Shell、访问云资源、修改数据库和发布生产环境的 Agent，错误半径完全不同。

LOW只读仓库

解释、搜索、Review。

MEDIUM可修改本地文件

代码编辑、测试、构建。

HIGH可访问外部服务

GitHub、数据库、云、内部 API。

CRITICAL可写生产环境

部署、删除、付款、敏感数据。

Anthropic 2026 年关于 agent containment 的工程文章直接把问题描述成“如何限制 blast radius”。成熟系统会按任务最小化权限，并要求可审批、可追踪、可回滚。

D6.9 · PARALLEL AGENTS

下一步：让多个 Coding Agent 并行处理独立任务

传统开发的很多瓶颈来自人类注意力串行：一个人同一时刻只能深度处理少量问题。Coding Agent 可以在独立 worktree / environment 中并行工作。

AGENT A修支付 BugRunning tests…
AGENT B补 API 测试PR ready
AGENT C升级依赖Resolving conflict…
AGENT D做代码 Review3 risks found

这会把人的瓶颈从“写代码速度”转移到：任务拆解、上下文准备、Review 带宽、测试基础设施和合并冲突。

D6.10 · SOFTWARE ECONOMICS

当软件供给成本下降，会发生什么？

01

长尾软件爆发

公司内部几十个人才会用的小工具，也可能值得专门开发。

02

原型 → 产品更快

创业者验证需求所需的工程资本下降。

03

定制化增加

“买通用 SaaS 并忍受不合适”与“自己做一个”之间的成本差缩小。

04

维护需求暴涨

软件数量越多，安全、测试、升级、可观测和技术债治理越重要。

05

代码本身贬值

代码供给变便宜后，用户、数据、工作流和分发会承担更多壁垒价值。

06

工程管理成为杠杆

能让多个 Agent 安全并行的人，产出边界可能明显扩大。

D6.11 · NON-DEVELOPER BUILDERS

非程序员最该补的能力：软件系统感

AI 降低了语法门槛，却提高了系统判断的重要性。对非程序员 Builder，优先掌握下面这些概念：

文件与目录知道代码大致放在哪里。
前端 / 后端 / 数据库知道一条请求经过哪些层。
API系统之间如何交换数据和动作。
状态哪些信息只在当前页面，哪些会持久保存。
权限谁能读、谁能写、哪些密钥不能暴露。
测试如何证明“改完没有把别的东西弄坏”。
日志出错时去哪找证据。
版本控制如何回滚、比较和审查改动。
目标你不需要亲手写完所有代码，但你必须逐渐拥有“看得懂系统、能判断风险、能验收结果”的能力。

D6.15 · SELF CHECK

本页自测

为什么 Vibe Coding 特别适合原型，却容易在长期项目中失控？

原型更关注快速验证，错误可逆且系统较小；长期项目会积累隐性约束、依赖和历史决策。如果没有 Spec、测试、架构和仓库级 Context，Agent 容易不断叠加局部正确但整体混乱的改动。

为什么测试在 Coding Agent 时代比以前更重要？

测试把“是否完成”变成机器可读取的反馈，让 Agent 自动运行—失败—修正，形成闭环，并显著减少人工逐次检查。

非程序员使用 AI 编程，最需要补的能力是什么？

系统感最重要：前后端、数据、API、状态、权限、版本控制、测试、日志和验收。

并行 Agent 最可能把新的瓶颈推到哪里？

任务拆解、Context 准备、测试基础设施、Review 带宽、冲突合并、权限和成本治理。
