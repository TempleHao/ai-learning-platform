DEEP DIVE 08

Multimodal、Voice 与 Realtime AI

文字聊天只是 AI 的第一个大众界面。真正更接近“智能体”的系统，需要同时看、听、说、理解屏幕、感知环境，并在用户说话时继续思考和行动。

能力理解图像、音频、视频、屏幕与文本为什么不是简单“多输入格式”。
产品知道 Realtime / Full Duplex / Barge-in / Latency 如何直接决定用户体验。
商业识别语音 Agent、视觉助手、现场服务、客服、销售和 Physical AI 的机会边界。
关键转折

当 AI 从“你问一句，我回一句”变成“持续看着环境、听你说话、允许你打断、同时调用后台工具”，交互范式就从 Chatbot 变成了一个持续运行的实时系统。

D8.1 · MODALITIES

多模态不是“支持上传图片”，而是不同感知空间被映射进同一个决策系统

TEXT

文本

离散 Token，结构清晰，最容易存储、检索和审计。

适合：知识、代码、规则、长文。
IMAGE

图像

空间信息密集，模型需要同时理解对象、关系、布局和视觉细节。

适合：文档、界面、场景、商品、医疗影像。
AUDIO

音频

除了内容，还有语速、停顿、情绪、噪声、说话人等时间信息。

适合：对话、客服、会议、现场协作。
VIDEO

视频

图像 + 时间。除了“有什么”，还要理解“发生了什么变化”。

适合：行为、运动、流程、监控、教学。
SCREEN

屏幕 / UI

视觉语义和可操作元素结合，必须理解状态和操作后果。

适合：Computer Use、软件自动化。
SENSOR

传感器 / 物理世界

连续、噪声、实时，并且行动会改变环境。

适合：机器人、自动驾驶、工业系统。
D8.2 · VISION

视觉能力的价值，是把“现实世界”变成模型可以推理的 Context

传统计算机视觉往往是一项任务一个模型：分类、检测、OCR、分割。多模态基础模型把这些能力压进更通用的视觉—语言空间后，同一个模型可以看截图解释报错、读表格、理解图表、比较商品、分析界面甚至作为 Agent 的观察器。

01

Visual Question Answering

对图片直接提问，不先强制转成固定标签。

02

Document Intelligence

结合文字、布局、表格、图表和页面结构理解文档。

03

UI Understanding

看懂按钮、菜单、页面状态，是 Computer Use 的感知层。

04

Vision + Reasoning

视觉不再只做识别，而进入多步推理和决策。

D8.3 · AUDIO

语音 AI 有两条完全不同的技术路线

CHAINED

ASR → LLM → TTS

先语音转文字，再交给文本模型，最后转回语音。

  • 可检查中间文本
  • 组件可替换
  • 容易接现有文本 Agent
  • 延迟通常更高
NATIVE AUDIO

Speech-to-Speech

模型直接处理和输出音频，不一定需要把每一步都显式转成文字。

  • 延迟更低
  • 更自然的语气和节奏
  • 能处理打断与实时 turn-taking
  • 调试与审计更复杂

因此，“语音 Agent”不是给 Chatbot 套一个 TTS。真正实时的语音产品需要单独处理音频流、打断、会话状态、工具调用和网络传输。

D8.4 · REALTIME

Realtime AI 的关键，不只是“快”，而是它能在时间流里存在

Listen持续接收音频 / 视觉流
→
Interpret判断用户意图和当前状态
→
Speak边生成边输出
↔
Barge-in用户可随时打断
↔
Delegate后台 Agent 同时搜索 / 用工具

OpenAI 2026 的 GPT-Live 把这件事拆成两层：Live 模型负责自然实时对话，后台 Agent 负责更重的推理、搜索和工具任务。前台可以继续交流，而后台工作不必阻塞整个对话。

D8.5 · VOICE ARCHITECTURES

三种 Voice Agent 架构，各自适合完全不同的产品

GPT-LIVE STYLE

实时前台 + 独立后台

语音模型负责完整对话体验，后台 Agent 负责复杂任务。

适合：客服、销售、实时助理。
REALTIME SESSION

一个实时模型承担对话 + 工具

音频、状态、工具和对话都放在同一实时 Session 内。

适合：逻辑较紧凑的语音应用。
CHAINED PIPELINE

ASR + Text Agent + TTS

每个阶段独立，最容易观察和替换。

适合：强审计、已有文本 Agent、流程型系统。
D8.6 · VIDEO + CONTINUOUS VISION

视频真正难的不是“每秒看一张图”，而是持续理解事件

视频比图片多了一个核心维度：时间。系统必须知道某个动作何时开始、持续多久、是否完成，以及前后状态是否改变。

采样问题抽帧太少会错过关键事件，太多又成本高。
状态连续性需要知道前几秒发生过什么，而不只是当前一帧。
主动发言真正实时助手要判断“什么时候应该主动说话”。
长期记忆持续视频流无法全部塞进 Context，需要事件摘要和外部状态。

这也是为什么“实时视觉助手”比单张图片问答难得多：它其实是 perception + event detection + memory + policy 的组合问题。

D8.7 · SCREEN + COMPUTER USE

屏幕是一种非常特殊的视觉：看见之后必须能正确行动

Computer Use 的基本循环可以写成：

Screenshot观察当前界面
→
Locate理解可点击对象
→
Decide根据任务选择操作
→
Act点击 / 输入 / 滚动
→
Verify重新观察状态

它最大的难点是脆弱性：同一页面的布局变化、弹窗、网络延迟、错误点击，都可能让下一步状态和计划完全不同。因此 Computer Use 必须和状态验证、权限、恢复机制一起设计。

D8.8 · INTERFACE SHIFT

下一代 AI 产品的界面，可能不再是“输入框”

VOICE

说出来

适合驾驶、走路、现场维修、客服、老人和无手交互。

CAMERA

让 AI 看见

用户不必描述“我看到什么”，直接把环境作为输入。

SCREEN

共享当前工作

AI 理解用户正在操作的软件，并直接辅助。

AMBIENT

环境式 AI

系统持续存在，根据事件而不是点击按钮被触发。

产品机会

每当输入成本下降，原本不会主动使用软件的人群和场景就会进入市场。语音和视觉最大的商业价值之一，是把“不会写 Prompt”这个门槛继续降下去。

D8.9 · LATENCY

在实时产品里，延迟不是基础设施指标，而是“智能感”的一部分

文字聊天延迟 2 秒可能还能接受；语音对话多等 2 秒，人会直接感觉“它没听懂”。Realtime 产品必须同时关注：

First Audio Latency用户说完后多久听见第一段响应？
Round-trip Time音频从用户到模型再回来需要多久？
Jitter延迟是否稳定，还是忽快忽慢？
Barge-in用户打断后，系统多久停下并重新听？
Tool Latency搜索 / 数据库 / 后台 Agent 是否拖慢对话？
Recovery断线或工具超时后能否自然继续？

OpenAI 2026 的实时语音工程文章把连接建立、媒体往返时间、抖动和丢包都视为核心体验问题，因为对话节奏本身就是产品质量。

D8.10 · SAFETY + PRIVACY

摄像头和麦克风让 AI 更有用，也让风险半径明显扩大

PRIVACY持续采集

音频 / 画面可能包含旁观者和环境敏感信息。

IDENTITY声音与人物

语音克隆、冒充和身份验证变得更重要。

ACTION实时建议

驾驶、医疗、工业等场景中的错误建议更难撤销。

RECORDING存储与留存

实时流是否保存、保存多久、谁能访问必须明确。

D8.15 · SELF CHECK

本页自测

为什么 Native Speech-to-Speech 和 ASR → LLM → TTS 不是一回事？

Chained Pipeline 把每个阶段拆开，易审计和替换；Native Speech-to-Speech 直接在音频空间进行理解和生成，延迟更低、自然度更高，但中间状态更难观察。

为什么视频理解比图像理解难很多？

视频必须理解时间、状态变化和事件边界，还要管理长时间流带来的 Context 与 Memory 问题。

为什么实时 AI 的延迟本身就是“智能感”的一部分？

人类对话依赖快速 turn-taking 和打断。如果系统响应慢、打断迟钝，即使回答内容正确，也会显得不理解当前互动。

什么时候不应该优先做语音 / 视觉？

当任务需要强审计、精确编辑、复杂结构化信息、环境隐私风险高，或文字输入已经足够高效时，多模态未必更优。
