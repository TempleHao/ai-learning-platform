DEEP DIVE 04

Agent：从软件工具
到数字劳动力

Agent 的关键变化，是把目标提升为软件的主要输入：用户说明要什么，系统自行决定下一步、调用工具、观察结果、修正计划并完成任务。

系统视角理解 Goal、Context、Model、Tools、Memory、Loop、Eval 与 Guardrails 如何组成 Agent。
工程视角理解为什么长任务失败、何时需要人审、预算和状态管理。
商业视角理解 Agent 为什么可能把 SaaS 从“卖工具”推向“卖完成的工作”。
先建立一个定义

这里把 Agent 定义为：围绕一个目标，根据当前状态动态选择下一步行动、调用工具并根据结果继续执行的 AI 系统。它的核心特征是一部分决策权被交给模型。

传统软件通常要求人决定每一步：打开页面、找字段、点击按钮。Agent 则把部分“下一步做什么”的判断交给模型。OpenAI 的 Agent 指南也把这类系统描述为能够代表用户以较高独立性执行工作流，并通过数据、行动和编排类工具与外部系统交互。

D4.1 · AGENT ANATOMY

Agent 是一套由模型、工具、状态与控制逻辑组成的运行系统

GOAL目标

成功到底是什么？什么时候算完成？

CONTEXT上下文

任务说明、文件、业务状态、规则与历史。

MODEL决策核心

理解、推理、规划并选择下一步。

TOOLS工具

搜索、数据库、代码、浏览器、API、企业软件。

MEMORY / STATE记忆与状态

记录发生过什么、当前走到哪一步。

LOOP执行循环

Observe → Decide → Act → Observe。

EVAL验收

结果是否满足目标？中间步骤是否可信？

GUARDRAILS边界

权限、预算、审批、禁止动作与审计日志。

系统直觉LLM 给 Agent “判断能力”；工具给它“手”；状态给它“连续性”；Eval 与 Guardrails 给它“边界”。
D4.2 · AUTONOMY LADDER

不要把所有“带 AI 的自动化”都叫 Agent

L0

Chat

人提问，模型回答。没有外部行动。

决策权：几乎全在人。
L1

Copilot

AI 生成建议，人决定是否采纳和执行。

决策权：人主导。
L2

Workflow

固定步骤中嵌入模型判断，流程仍由人预定义。

决策权：局部交给模型。
L3

Agent

模型根据状态动态选择工具和下一步。

决策权：路径部分开放。
L4

Long-running Agent

跨小时 / 天持续执行，管理任务、状态、失败与恢复。

决策权：更高自主性。
L5

Delegated Worker

人只定义目标、预算和边界，系统负责大部分执行与交付。

商业形态：更接近数字劳动力。
自主性必须与任务风险匹配

任务越稳定、监管越严格、错误越昂贵，就越应该把决策留在 Workflow、规则和审批节点里。Agent 最擅长处理路径不确定、需要动态判断的任务。

D4.3 · WORKFLOW vs AGENT

成熟 Agent 系统依靠受控自治，而非无限自由度

Anthropic 在其 Agent 工程总结中区分了两类系统：预定义代码路径的 workflow，以及由模型动态决定过程和工具使用的 agent。其经验表明，简单、可组合的模式往往更容易取得稳定结果。

WORKFLOW

可预测路径

步骤、分支和检查点可以提前定义。

  • 更稳定
  • 更容易测试
  • 成本更可控
  • 适合高风险流程
AGENT

开放路径

任务需要搜索、尝试、反复决策，无法提前穷举步骤。

  • 适合开放问题
  • 适应性更强
  • 错误路径更多
  • 更需要 Eval 与预算边界

一个常见的成熟架构其实是：外层 Workflow 规定阶段和权限，内层 Agent 在某个阶段里自由探索。 这样既保留适应性，又把错误半径限制住。

D4.4 · RELIABILITY COMPOUNDS

为什么“单步 95% 正确”仍然可能做不好长任务？

长任务要求很多步骤连续成功。为了建立直觉，可以暂时把每一步看成独立事件，此时总体成功率会近似按连乘衰减。这个简化模型足以解释为什么 Agent 需要检查点、重试和局部验收。

INTERACTIVE · RELIABILITY

长任务成功率直觉实验

59.9%

教学简化：假设每步独立且失败后无重试。真实 Agent 的错误可能相关，也可以通过检查点、重试和人类接管显著改善。
01

局部验收

不要等 20 步全部结束才检查。每个高风险阶段都验证输出。

02

可恢复状态

失败时从最近检查点继续，避免整段任务重新执行。

03

预算边界

限制最大步骤、时间、Token、工具调用和金钱成本。

04

Human Handoff

超过失败阈值或进入高风险动作时，把控制权交还给人。

D4.5 · TOOLS + COMPUTER USE

Agent 的“行动能力”有两条主要路径：API 与界面操作

API / TOOL CALL

结构化调用

模型选择一个明确工具，并生成经过 schema 约束的参数。

  • 更稳定
  • 权限容易控制
  • 容易审计
  • 需要系统提供 API
COMPUTER USE

像人一样操作界面

模型观察屏幕、点击、输入并根据界面变化继续行动。

  • 能覆盖遗留软件
  • 不依赖 API
  • 界面变化会造成脆弱性
  • 更需要验证与审批

Computer Use 的战略意义很大：它让 AI 可以进入没有 API 的软件和网页。但它也把传统 RPA 的脆弱性与模型的不确定性叠加在一起，所以真正生产化通常需要截图 / 状态验证、失败恢复和敏感动作审批。

D4.6 · MEMORY + CONTEXT

Agent 的“记忆”至少包含四类不同状态

WORKING

工作记忆

当前任务里的短期上下文、计划和中间结果。

EPISODIC

经历记忆

过去做过什么、哪些路径失败、用户曾经怎样纠正。

SEMANTIC

知识记忆

文档、数据库、知识库和可检索事实。

STATE

业务状态

CRM、订单、工单、Git、日历等真实系统当前状态。

很多“Agent 记忆问题”源于状态设计不清：系统没有决定哪些信息留在对话里、哪些进数据库、哪些通过检索获得、哪些必须从 source of truth 实时读取。

D4.7 · MULTI-AGENT

Multi-Agent 是组织复杂度的一种方式，需要明确收益再使用

把一个系统拆成 Research Agent、Coding Agent、Reviewer Agent、Manager Agent，确实可以让职责更清晰；但每增加一个 Agent，也增加上下文传递、冲突、延迟、成本和调试难度。

适合拆不同任务需要明显不同工具、权限、上下文或评测标准。
适合拆专家之间可以并行工作，再由一个明确机制汇总。
不要拆只是为了“角色扮演”而创建多个几乎相同的模型实例。
不要拆一个 Agent + 明确工具就能完成的任务，没必要引入通信复杂度。
工程原则

先做一个 Agent；只有当单 Agent 的上下文、权限或职责真的冲突时，再拆成多 Agent。

D4.8 · CONTROL PLANE

企业采购 Agent 时，最看重的是可控性与结果责任

IDENTITY身份

谁启动了任务？Agent 代表谁行动？

PERMISSION权限

能读什么、写什么、最大金额 / 范围是多少？

APPROVAL审批

哪些不可逆动作必须暂停等待人确认？

TRACE轨迹

模型想了什么不重要，系统做了什么必须可追踪。

EVAL评测

每个版本在真实任务分布上成功率是否提高？

BUDGET预算

最大步骤、时间、成本、并发和重试。

RECOVERY恢复

失败后如何回滚、补偿、重跑或交给人？

AUDIT审计

敏感工具调用、数据访问和审批需要留痕。

官方工程指南也反复强调这一点：guardrails 不能替代身份、授权和传统软件安全；敏感或不可逆动作应当使用人工审批，高风险流程需要明确的失败阈值与人类接管。

D4.10 · AGENT ECONOMY

如果 Agent 可靠性跨阈值，软件的收费对象可能从“席位”变成“工作”

SaaS卖工具 / 席位
→
Copilot卖增强后的用户生产力
→
Agent卖自动完成的任务
→
Outcome按结果 / 交易 / 节省收费

SaaS 的价值计量方式可能发生变化。如果客户只提出“把这个客户名单清洗完”“把这批发票对账完”“把这个代码迁移完成”，软件供应商就会开始和内部人工、外包、BPO、咨询费用进入同一个预算池竞争。

01

Seat → Task

从按用户数收费转向按任务量、调用量或自动化量收费。

02

Task → Outcome

当系统能承担结果责任，收费进一步靠近“完成了什么”。

03

Software → Labor Budget

AI 公司可以从 IT 预算进一步进入人工与外包预算。

04

Tool → Operator

软件厂商从提供功能，逐渐变成替客户运行流程的运营者。

D4.11 · ORGANIZATION

企业最先变化的往往是管理半径和任务边界

在短期里，更现实的变化往往是：一个人可以管理更多并行任务；初级工作被 AI 先做第一遍；高级人员从“亲自执行”转向定义目标、设计流程、处理异常和承担责任。

旧组织经理 → 多名执行人员 → 软件工具
→
过渡组织经理 / 专家 → AI Copilot + 少量人工执行
→
Agent-native人负责目标与例外 → 多个数字执行单元承担标准任务

真正重要的新能力因此可能是：任务定义、上下文设计、评测、异常管理和责任判断。 一个不会训练模型的人，仍然可以成为非常强的 Agent Operator / AI Workflow Architect。

D4.12 · FRONTIER SNAPSHOT · 2026

Agent 已经从“会不会做”进入“能否稳定托管”阶段

66.3%OSWorld 上最佳 Agent 的计算机任务准确率相比此前约 12% 大幅提升，但仍约三次失败一次。
88%受访组织报告已使用 AIAI 普及很广，但这不代表深度自主流程已普及。
个位数多数企业职能里的 Agent 实际部署率能力增长明显快于组织重构。

这三个数字合在一起非常关键：Agent 已经拥有足够能力进入生产候选区，但可靠性、权限、系统集成和组织责任仍是大规模部署的主要摩擦。因此未来几年最有价值的工程和商业问题，很可能集中在“最后一公里控制面”。

D4.13 · RISK SURFACE

Agent 风险的关键在于错误会产生真实副作用

INJECTION

提示注入

外部网页、邮件或文件可能诱导 Agent 偏离原任务。

AUTHORITY

越权

模型尝试读取或修改超出用户授权的数据。

IRREVERSIBLE

不可逆动作

付款、删除、发信、取消订单等动作出错后代价高。

LOOP

失控循环

反复重试、工具调用、成本累积而无法停止。

STATE

状态漂移

模型以为系统处在某个状态，但真实数据库 / UI 已改变。

ACCOUNTABILITY

责任归属

Agent 做错以后，是模型、软件商、企业还是审批人负责？

D4.14 · DESIGN CHECKLIST

要不要把一个流程 Agent 化？先回答九个问题

目标

“完成”能不能清楚定义？

路径

步骤真的难以提前写死吗？如果不难，Workflow 可能更好。

工具

Agent 要读什么、写什么、调用什么系统？

验证

每一步或最终结果能否自动检查？

错误代价

一次失败的真实成本是多少？可逆吗？

审批

哪些动作必须人确认？

预算

最大步骤、时间、调用和金额是多少？

恢复

失败后从哪里继续？怎么回滚？

经济性

把模型、人审、失败重做和运维算进去，仍然比旧流程好吗？

D4.15 · SELF CHECK

本页自测

Agent 和 Workflow 最关键的区别是什么？

Workflow 的路径主要由人提前定义；Agent 把“下一步做什么”的部分决策权交给模型，允许根据状态动态选择行动。

为什么长任务 Agent 比单轮问答更难可靠？

因为任务由多个依赖步骤组成，错误会传播和累积；每一步还会改变外部状态。因此需要中间验收、可恢复状态、重试与停止条件。

为什么 Computer Use 很重要但也更危险？

它能进入没有 API 的遗留系统，但界面更脆弱、状态更难结构化验证，而且点击和输入会直接产生现实副作用。

Agent Economy 的商业本质是什么？

软件从帮助人操作工具，逐渐走向直接完成任务。当可靠性和责任体系足够成熟时，收费可能从席位转向任务和结果，并进入人工与外包预算。
