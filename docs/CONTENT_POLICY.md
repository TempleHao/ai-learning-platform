# AI Learning OS · 内容、来源与版本规范

> 目标：让这个项目几年后仍然可读、可验证、可更新，并始终保持教材级的结构、证据与语言质量。

## 1. 三层知识

### Stable
相对稳定的基础知识：经典论文、基本原理、重要历史、系统架构和长期有效的经济逻辑。

要求：
- 优先引用论文、标准、官方文档和一手历史资料。
- 不用“当前最强”“目前价格”等会快速过时的表达承载核心定义。
- 重大修订进入 CHANGELOG。

### Frontier
快速变化内容：模型能力、Benchmark、Agent、机器人、芯片、价格、企业采用、融资、监管和市场结构。

要求：
- 必须标明年份或“Frontier Snapshot”。
- 优先使用最近的权威来源。
- 默认每 90 天进入一次复核队列；重大事件随时更新。
- 旧数据不删除历史痕迹，更新时在 CHANGELOG 记录。

### Lab
个人实验和真实项目。

每个 Lab 至少记录：
1. 任务；
2. 输入 / 数据；
3. 使用的模型或工具；
4. 验收标准；
5. 实际结果；
6. 失败点；
7. 下一轮改进。

## 2. 来源优先级

从高到低优先：
1. 原始论文 / 标准 / 法规 / 官方数据；
2. 官方公司技术与产品文档；
3. 大学、研究机构、国际组织报告；
4. 高质量新闻与行业研究；
5. 社区讨论（只用于体验、观点和发现线索）。

不能把二手文章当成原始证据。

## 3. 事实与判断分离

页面中的内容尽量区分：
- **Fact**：来源可验证的事实。
- **Interpretation**：基于事实的解释。
- **Hypothesis**：尚未验证的未来判断。
- **Scenario**：情景推演，不声明必然发生。

## 4. 章节状态

- `draft`：结构或证据尚不完整。
- `reviewed`：已完成一轮事实和结构检查。
- `stable`：稳定核心内容，可作为基线学习。
- `frontier`：明确包含需要持续更新的时效数据。

当前 HTML 章节顶部的 Stable / Frontier 标签承担第一阶段的可视状态标记。

## 5. 更新原则

更新优先级：
1. 错误事实；
2. 已失效的 Frontier 数据；
3. 会改变商业判断的重大能力变化；
4. 新的关键论文 / 技术路线；
5. 表达与 UI 优化。

## 6. 日期规则

- 所有快速变化数据必须能知道“这是哪一年的状态”。
- 相对日期（今年、最近、现在）尽量同时给绝对年份。
- 历史章节不把 2026 的产品状态写进 Stable 定义。

## 7. 纠错规则

发现事实错误时：
- 直接修正文；
- 在 CHANGELOG 标记 correction；
- 如错误影响已有结论，同时修正结论和相关 Lab / 自测。

## 8. 项目工程记忆

GitHub 是项目的长期工程记忆：
- Issues = 尚未完成的工作；
- Commit history = 实际变化；
- CHANGELOG = 对学习者有意义的版本变化；
- docs/ = 可编辑源稿；
- site/ = 在线学习界面。


## 9. 文风与措辞

AI Learning OS 的文字必须像教材、工程手册和研究笔记，避免明显的生成式模板腔。

### 优先采用
- 直接判断：先给结论，再解释依据。
- 定义句：明确主语、对象、边界和作用。
- 因果句：说明“为什么会这样”。
- 动作句：告诉学习者下一步做什么。
- 精确比较：指出两个概念分别处在哪个层级、负责什么。

### 限制使用
以下句式只有在逻辑上确有必要时才使用，禁止连续或习惯性出现：
- `不是 X，而是 Y`
- `不只是 X，而是 Y`
- `真正的 X 不是……`
- `重点不是……而是……`
- `不要只……而要……`

### 改写原则
把模板式对比改成更准确的表达：
- 写清 **X 的职责** 和 **Y 的职责**；
- 写清 **变化方向**，例如“从 A 扩展到 B”；
- 写清 **因果关系**，例如“由于 A，B 成为瓶颈”；
- 写清 **判断标准**，例如“商业化取决于可靠性、成本与工作流嵌入”。

允许保留必要的逻辑否定，例如“并不成立”“无法直接推出”“不等同于”，但应优先使用精确关系描述，避免为了制造语气而强行对立。
